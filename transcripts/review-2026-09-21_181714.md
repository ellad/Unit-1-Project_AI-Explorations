## Agent

Investigated further via web search/fetch against EcoLogits' site, GitHub repo, and the underlying "Lights, Camera, Carbon" scaling-law paper (arXiv:2607.04553).

**Finding:** The claim wasn't fabricated, but was mis-sourced. EcoLogits' own video-generation blog post and GitHub repo don't cover Veo 3.1 — but the underlying paper it's built on does estimate Veo 3.1 specifically, alongside Sora 2.0 Pro, Seedance, and Runway Gen-4.5. It does this indirectly: since video diffusion models run near their thermal design power, the authors clock API response times for real Veo 3.1 requests, assume a hardware platform (TPU v6e), model power draw as ~90% of TDP, and run 10,000 Monte Carlo simulations. Result for one 8-second, 720p clip: **19.8–43.4 Wh, mean ~30.8 Wh** (GPU/accelerator energy only, 9.65% MAPE, 18.21% max error).

Two things the original spec got wrong about this number:
- "PUE 1.09 / WUE 0.999" isn't in that paper at all — the paper explicitly says it only accounts for GPU energy. PUE 1.09 is real (Google's actual reported 2025 fleet-wide PUE), but it's a separate assumption bolted onto the paper's number, not something EcoLogits documents together as a Veo 3.1 example.
- There's no per-resolution/per-duration breakdown for Veo specifically — only the one tested configuration (8s, 720p) has an actual number.

**Recommendation given:**

1. Keep Veo 3.1 as the video model, but cite arXiv:2607.04553 §4.4 directly, not "EcoLogits," for the energy range.
2. Drop the free duration/resolution inputs. Make video a fixed-benchmark entry (like the existing "coding/agent session" and image-proxy patterns already in this calculator): one reference clip (8 seconds, 720p), scaled by output count and the retry multiplier only.
3. Gross up to facility energy with PUE 1.09, reusing EcoLogits' actual published Google provider default (already used for the calculator's Gemini rows) — labeled as a separate assumption stacked on top of the paper's number.
4. For water, drop "WUE 0.999" and instead reuse the same NREL 0.47 gal/kWh derived-water approach already used for image generation and the router baseline.
5. For carbon, convert using the grid-intensity logic already in the calculator, not a new constant.
6. Sharpen the uncertainty language to say the number is inferred from API latency and an assumed hardware platform, not measured — an even weaker evidentiary basis than the image proxy.
